# 团队项目管理需求拆解（V1）

## 1. 文档目的
- 将现有 PRD 转换为可执行的需求基线，便于产品、设计、研发、测试协同推进。
- 输出重点包含：功能清单、优先级建议、核心用例、验收标准、阶段划分建议。
- 本文基于 `README.md`、`docs.zip` 内的 `PRD_v1.md`、`architecture_v1.md`、`ADR-0001-tech-stack.md` 整理。

## 2. 产品目标与边界

### 2.1 业务目标
- 建立统一的研发事项入口，避免需求、Bug、日常工作分散在多个工具。
- 建立需求到执行的闭环链路，让评审、排期、执行、汇报可追踪。
- 提供团队级排期视图，识别成员时间冲突和进度偏差。
- 降低日报周报整理成本，让工作日志和执行进度自动沉淀为汇报内容。

### 2.2 目标用户
- 超级管理员：负责系统级配置、组织策略、权限模板。
- 组织管理员：负责成员、角色、权限策略维护。
- 项目管理员：负责项目管理、成员分配、排期控制。
- 需求负责人：负责需求录入、推进、发起评审。
- 执行成员：负责研发、测试、设计类执行项推进和日志填写。
- 只读访客：查看项目和报表，不参与写操作。

### 2.3 V1 范围定义
| 类型 | 内容 |
| --- | --- |
| V1 必做 | 登录、成员与权限、工作台、需求池、项目总览、执行管理、日常执行、自动日报、基础报表、审计日志 |
| V1 建议做 | 轻量工时日志、缺陷管理、站内通知、团队甘特冲突检测、钉钉绑定与推送 |
| V1 不做 | 多组织多租户、复杂工时核算、甘特拖拽改期、钉钉内完整应用替代 |

### 2.4 关键产品原则
- 统一实体：研发事项统一使用 `Execution`，不再拆分独立 `Task`。
- 项目与执行分离：项目承载管理视角，执行承载协同视角。
- 权限双重校验：前端控制可见性，后端控制安全边界。
- 汇报自动化：日报周报来源于真实执行行为和日志记录，不依赖二次录入。

## 5. 核心用例

### UC-01 需求负责人提交需求并发起评审
- 参与角色：需求负责人
- 前置条件：用户已登录，拥有需求创建和编辑权限。
- 触发条件：录入完需求信息，准备进入评审。
- 主流程：
  1. 用户在需求池创建需求并填写标题、描述、负责人、优先级等基础信息。
  2. 系统将需求保存为草稿或需求了解状态。
  3. 用户补充验收标准、影响范围、依赖风险、方案结论。
  4. 用户点击“发起评审”。
  5. 系统执行成熟度检查。
  6. 检查通过后，系统创建评审记录并将需求流转到“待评审”。
- 异常流程：
  1. 若成熟度检查未通过，系统明确提示缺失项，不允许进入评审。
  2. 若用户无权限，后端直接返回 403。
- 结果：需求进入标准评审流程，且留痕可追踪。

### UC-02 项目管理员批量将需求生成执行
- 参与角色：项目管理员、需求负责人
- 前置条件：所选需求已处于允许生成执行的状态。
- 触发条件：用户在需求池中勾选多个需求，点击“生成执行”。
- 主流程：
  1. 用户选择目标项目、执行类型、负责人、计划时间。
  2. 系统校验需求状态、项目合法性、权限和幂等键。
  3. 系统批量创建执行，并建立需求与执行的双向关联。
  4. 系统返回成功列表和跳过列表。
- 异常流程：
  1. 若部分需求不符合条件，系统返回 `skipped_requirement_ids`，其余合法需求继续处理。
  2. 若重复提交相同幂等键，系统不重复创建。
- 结果：需求正式转入执行阶段，链路可追踪。

### UC-03 执行成员拆分子执行并推进进度
- 参与角色：执行成员、项目管理员
- 前置条件：用户具备执行编辑权限，执行已分配到本人或所在项目。
- 触发条件：进入执行详情页后进行协同操作。
- 主流程：
  1. 用户在根执行下新增子执行。
  2. 用户填写子执行负责人、计划开始、计划结束、预计工时。
  3. 用户推进子执行状态和实际进度。
  4. 系统自动递归回写父执行的计划时间、实际时间和进度。
  5. 系统记录操作日志。
- 异常流程：
  1. 若依赖未满足且业务规则限制推进，系统提示阻断原因。
  2. 若用户尝试关闭未完成的父执行，系统提示存在未完成子执行。
- 结果：执行树状态一致，管理层和成员看到的是同一份进度数据。

### UC-04 执行成员填写跨天工作日志并生成日报
- 参与角色：执行成员
- 前置条件：执行已存在，用户具备日志填写权限。
- 触发条件：用户需要记录当天工作内容。
- 主流程：
  1. 用户在执行中点击耗时或工作日志入口。
  2. 用户填写工作日期、工作内容、耗时。
  3. 系统保存日志，并将该日志纳入日报采集范围。
  4. 用户在报告页点击“生成今日日报”。
  5. 系统聚合执行变化、工作日志、日常执行，生成日报草稿。
  6. 用户编辑草稿并导出或复制。
- 异常流程：
  1. 若日志保存失败，系统允许重试，不应丢失已输入内容。
  2. 若某条日常执行被标记为“不纳入汇报”，生成日报时需排除。
- 结果：日报基于真实行为自动生成，减少人工整理。

### UC-05 项目管理员查看团队甘特并识别冲突
- 参与角色：项目管理员、组织管理员
- 前置条件：执行存在计划开始与计划结束时间。
- 触发条件：用户进入团队甘特页面。
- 主流程：
  1. 系统按成员聚合执行区间。
  2. 页面展示成员时间轴上的执行分布。
  3. 系统对同成员同时间段的执行重叠做冲突检测。
  4. 页面显示冲突汇总卡片，并支持点击查看详情。
- 异常流程：
  1. 若执行未排期，不参与冲突计算，但在工作台提示“未排期执行”。
- 结果：管理者可快速发现资源冲突并调整排期。

### UC-06 测试成员批量提交缺陷并通知负责人
- 参与角色：测试成员、执行负责人、项目管理员
- 前置条件：缺陷模块已启用，用户具备缺陷创建权限。
- 触发条件：测试阶段集中录入 Bug。
- 主流程：
  1. 测试成员批量录入多条缺陷草稿。
  2. 用户统一编辑优先级、严重级别、挂靠对象。
  3. 用户执行统一提交。
  4. 系统写入缺陷记录，并向对应负责人发送通知。
- 异常流程：
  1. 若挂靠对象无效，系统阻止提交该条数据并提示问题。
  2. 若钉钉通知失败，站内通知仍需送达，失败进入重试队列。
- 结果：缺陷统一进入系统，响应链路明确。

### UC-07 管理员查看执行统计与成员投入
- 参与角色：组织管理员、项目管理员
- 前置条件：执行、工作日志、日报数据已沉淀。
- 触发条件：用户进入统计报表页。
- 主流程：
  1. 用户按项目、执行、成员、时间范围筛选。
  2. 系统展示计划开始、计划结束、实际完成和成员工作内容。
  3. 用户可下钻查看某成员在某天参与的子执行和日志内容。
- 结果：管理层可以做计划与实际偏差分析，并核查投入明细。

## 6. 核心规则与数据约束

### 6.1 状态规则
- 需求状态：草稿 -> 需求了解 -> 需求确认 -> 待评审 -> 已评审 -> 排期中 -> 开发中 -> 已上线 -> 关闭。
- 执行状态：待开始 -> 进行中 -> 阻塞 -> 待验收 -> 已完成 -> 已关闭。
- 日常执行状态：未开始 -> 进行中 -> 完成 / 搁置。
- 评审记录是事件，可多次发生，不应覆盖历史数据。

### 6.2 执行汇总规则
- 父执行计划开始取所有子执行最早计划开始。
- 父执行计划结束取所有子执行最晚计划结束。
- 父执行实际开始取所有子执行最早实际开始。
- 父执行实际完成仅在全部子执行完成后产生，取最晚实际完成。
- 父执行实际进度按子执行预计工时加权汇总；未填预计工时则取平均值。
- 计划进度按当前日期处于计划区间的位置自动计算。

### 6.3 权限规则
- 页面、按钮、关键动作必须有明确权限点。
- 前端按钮不可见不等于安全，所有写接口后端必须做权限校验。
- 越权访问统一返回 403 类错误码。

### 6.4 审计规则
- 以下行为必须写审计日志：需求评审、状态流转、执行分配、排期修改、缺陷提交、权限变更。
- 审计日志需记录操作人、操作对象、动作、时间、变更摘要、请求标识。

## 7. 验收标准

### 7.1 P0 验收标准
- 用户使用正确账号密码可以登录系统，并获得符合角色的菜单与按钮权限。
- 需求池支持创建、编辑、筛选、状态流转，并能保存常用视图。
- 发起评审前若缺少验收标准、依赖风险、负责人等关键信息，系统必须阻止提交并明确提示。
- 需求支持多次评审，历史评审记录可追溯，不被覆盖。
- 多选需求批量生成执行时，系统能正确建立需求与执行的双向关联。
- 执行支持树形结构，子执行变更后父执行的计划时间、实际时间、进度可以自动递归汇总。
- 执行成员可以填写每日工作日志和耗时，且日志可进入日报采集范围。
- 日常执行支持一行输入回车创建、快捷日期词、筛选排序和“不纳入汇报”开关。
- 报告页可以一键生成日报草稿，并允许编辑、复制、导出。
- 无权限用户即使绕过前端按钮，也无法通过接口完成写操作。
- 关键动作在审计日志中可查到操作轨迹。

### 7.2 P1 验收标准
- 缺陷支持挂靠到项目或执行，并支持批量草稿统一提交。
- 缺陷提交后能通知到对应负责人；钉钉失败时站内消息不受影响。
- 团队甘特可按成员展示执行分布，并高亮同成员同时间段冲突。
- 执行甘特支持总览模式和详情模式，能查看计划进度、实际进度、计划时间和实际完成时间。
- 周报支持自动生成、编辑与导出。
- 管理员统计页支持按项目、成员、时间范围筛选，并可下钻到成员当日日志。
- 用户完成钉钉绑定后，可接收执行指派、阻塞、评审结论、日报生成等消息推送。

## 8. 研发实现建议
- 后端先优先完成权限、需求、执行、日志、日报五条主链路，再扩展缺陷和通知。
- 批量写操作统一要求幂等键，避免重复生成执行或重复提交缺陷。
- 甘特冲突检测和日报生成建议走异步任务，避免阻塞主交易接口。
- 日志、权限、状态流转建议先统一抽象，减少后续功能扩展时的重复实现。

## 9. 测试重点
- 权限穿透测试：页面不可见、接口是否仍可能被调用。
- 递归汇总测试：多层执行树在各种状态组合下是否正确回写。
- 幂等测试：重复点击批量生成执行或统一提交缺陷是否重复入库。
- 汇报准确性测试：日报是否正确排除不纳入汇报的事项。
- 冲突检测测试：同一成员、跨天区间、边界时间点是否正确识别。
- 通知可靠性测试：站内通知成功、钉钉失败重试、死信告警是否生效。
